The DB-06 and DB-10 importers no longer create tables. The migration is the single definition.

### `legacy_history_events`

| Column | Meaning |
|---|---|
| `record_id` | Stable source key. Events: the ledger movement key. Receipts: `<instance>/receipt/<source product id>/<day>/<unit>` |
| `warehouse_key` | `estoquefacil-fb15/1/local/1` (warehouse = branch 1) |
| `event_date` | Date of the individual record. `source_date` is the verified snapshot date, **null unless verified** |
| `event_type` | DB-07 type (`pos_sale`, `invoice_sale`, `sale_correction`, `supplier_return`, `loss`, `warranty_exchange`, `internal_outbound`, `pending_document`, `canceled_document`, `transfer`, `unverified_outbound`) or `receipt` |
| `event_class` | `sale` (pos_sale, invoice_sale) · `receipt` · `return` (sale_correction, supplier_return) · `other_outbound` (everything else) |
| `is_demand` | True only for `pos_sale` and `invoice_sale` |
| `quantity` / `signed_quantity` | Base units. `quantity = abs(signed_quantity)`, `>= 0`. A negative-day correction keeps its sign in `signed_quantity` |
| `unit_cost` | Receipts only: quantity-weighted invoice cost per base unit of the posted, known-cost lines of that product and day; null otherwise |
| `stock_availability` | `available`, `stockout`, `unknown` or `uncovered`; default and real value `unknown`. `available` only on a sale day |

DB-07 `reject` rows (the document does not move stock) and DB-09 receipts with no resolvable quantity are not staged. They are rejections.

**Not staged on purpose:** DB-08 `corrections.csv`. The ledger events already hold the net daily sales and the 18 negative-day corrections, so applying the 1,891 ticket-level corrections again would double count. They stay quality evidence for DB-14.

### `legacy_coverage_ranges` (DB-12 day-level evidence)

`day_status` is the DB-12 status. Two derived columns are generated by PostgreSQL so no loader can diverge:

| `day_status` | `coverage` (API-01 vocabulary) | `uncensored` (usable for demand calibration) |
|---|---|---|
| `sale` | `available` | yes |
| `true_zero` | `available` | yes |
| `zero_unknown_availability` | `unknown` | no |
| `unknown_quantity` | `unknown` | no |
| `known_stockout` | `stockout` | no |
| `calendar_gap` | `uncovered` | no |

A missing day is never zero demand, and unknown availability is never a stockout.

**Day-level extract:** available outside Git at `~/.estoquefacil-legacy-work/fb15/out/db12/series.csv.gz` (sha256 prefix `86a791d2d95c12d8`; columns `product_key,day,status,demand,receipts,available,uncensored`; 5,263,168 product-days, matching the DB-12 summary) with `series_index.csv` (prefix `2f32b23260bbe566`, 6,928 series). **DB-02 loads it into `legacy_coverage_ranges` (409,640 runs) and `legacy_coverage_series`. The local artifact is the source, not the API's dependency.** The API reads the tables, so a deployment needs no local file.

## Preview (`legacy/preview.py`)

- Returns `LegacyImportPreview` as a dict. `total_rows = valid + rejected + duplicate`. `invalid` means a manifest failure or at least one rejected row. It doesn't block importing the valid rows.
- Read-only: the connection is set to READ ONLY, which PostgreSQL enforces, and rolled back. A record already in `legacy_history_events` for the warehouse counts as a duplicate.
- Diagnostics are capped at 200 and counts stay exact. Reason codes carry no source values: `unknown_product`, `product_unknown_unit`, `invalid_date`, `invalid_quantity`, `unknown_event_type`, `document_does_not_move_stock`, `receipt_quantity_unavailable`, `missing_record_key`, `manifest_invalid`.

```sh
cd backend
python -m legacy.preview <extract-dir> <out-dir> [--pg-socket DIR --pg-port N --pg-db NAME]
```
